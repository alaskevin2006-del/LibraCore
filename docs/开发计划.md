# 图书馆管理系统｜第8—15周开发工期与满分验收计划

> **版本**：v1.0｜**制定日期**：2026-10-25（第7周结束）  
> **目标**：最晚第15周完成并提交，按新版评分 PPT 的七项维度争取 **100/100**。  
> **依据**：《软件工程初级实训课程项目作业考核评分方案（图书管理）(1).pptx》（新版）、《大作业开发报告基本格式.pptx》；本组此前确定的 C++ 前后端分离、四人两组、云端后端方案。  
> **性质**：本文的具体排期、技术分工、验收门槛和学习时长均为**小组自定计划**，不是教师规定的时间节点或技术选型。PPT 的业务及创新清单为**举例**，不是全部强制实现或逐项独立加分。

## 0. 项目范围与排期总则

### 0.1 边界与优先级

- **必须首先完成**：基于 Qt + MySQL 的图书管理系统；借书人端与管理员端；图书、读者、借还和借阅记录；业务异常处理；良好的代码结构、数据库一致性、UI、测试、协作过程和文档。
- **从第8周前置建设**：真实联网。Windows Qt 客户端走 HTTPS/REST API；Drogon 后端和 MySQL 部署在 Linux 云服务器。联网本身在评分 PPT 中属于进阶方向，但团队已经确定采用这一技术路线。
- **优先的 PPT 内创新**：多终端数据共享（既有网络架构）、借阅统计/可视化、批量导入导出、图书超期提醒；分类推荐酌情实施。
- **放到最后**：Android 手机端检索与借阅；仅在桌面端、工程质量和答辩材料均达到验收线后启动，不为了 APK 延误主项目。
- **本次不承诺**：座位预约、扫码借阅、复杂 AI 推荐、独立微服务、Kubernetes、极端高并发指标。图书预约/续借也不是新版评分 PPT 的基础功能考点，**不作为本轮必做范围**。
- **核心代码由组员编写**：Agent 用于解释、审查、协助定位错误、提出测试场景，不直接代写主要业务模块。

### 0.3 固定技术栈与职责边界

| 部分 | 技术 | 谁负责什么 |
|---|---|---|
| Windows 客户端 | **C++17、Qt 6、QML/Qt Quick、Qt Network** | 页面、控件、信号/槽、状态、HTTP 请求、异常反馈 |
| 后端（云服务器） | **C++17、Drogon** | REST API、认证鉴权、借阅规则、事务、日志 |
| 数据层（云服务器） | **MySQL 8、SQL** | 用户/书目/实体副本/借阅记录、约束、持久化、查询 |
| 通信与契约 | **HTTPS、JSON、OpenAPI** | 统一接口字段、错误码；前后端并行开发 |
| 运维部署 | **Ubuntu、Docker Compose、Nginx、SSH** | Drogon/MySQL/Nginx 部署、TLS、配置、备份 |
| 构建与协作 | **CMake、Git、GitHub** | 独立分支、PR、代码审查、版本记录 |
| 测试 | **GoogleTest、Qt Quick Test、API 测试脚本、k6（后期）** | 单测、接口/集成、GUI、并发冲突验证 |
| 自动化 | **CTest、GitHub Actions（基础版）** | 每次合并触发构建与基本测试，保存结果 |
| 手机端（最后） | **Qt for Android、JDK、Android SDK/NDK、ADB** | 适配 QML、真机调试、生成签名 APK |

**结构**：Qt 客户端 → HTTPS/JSON → Nginx → Drogon（Controller → Service → Repository）→ MySQL。数据库只允许后端内部连接；前端组和后端组可独立开发并通过 API 联调。

**人员模式**：前端组（主力 1 + 辅助 1）；后端组（主力 1 + 辅助 1）。主力负责关键设计与集成，辅助必须有独立的界面/数据库/测试/文档等可验证产出。每个主要 Issue 标明责任人、评审人和验收证据。

## 1. 分周执行计划

### 第8周｜10/26—11/01：让最小联网系统真实运行

**本周目标**：避免只搭空架子；至少实现“Qt 点击查询 → 访问云端 Drogon → MySQL 返回若干图书 → 界面显示”。

**行动安排**：周初举行**组会1（正式纪要）**，确定需求边界、四人分工、任务优先级、接口负责人；周中举行一次 20–30 分钟接口评审；周末四人共同联调与演示，记录问题和修改方案。

**M1 验收**：全新 Windows 客户端连接公网服务端，服务端查 MySQL 返回真实数据；至少一次完整 Git PR；留存架构图、ER 图、接口草案、组会纪要和冒烟测试记录。**若失败，第9周前两天先解决链路，不再扩展 UI。**

**本周目标**：利用时间窗口完成工作量最大的基础 CRUD 模块，实现“管理员操作 → 数据库生效 → 读者端可查询”。

**行动安排**：周初只承诺“批量导入导出”一个新增业务；完成后才开始逾期提醒；推荐功能不影响其他工作。周末审查**每项创新是否真实运行且与图书管理流程结合**，不把功能数量当作评分依据。

## 2. 每周固定执行的研发流程（第8—15周持续）

| 时间/频率 | 工作动作 | 最小记录 | 作用 |
|---|---|---|---|
| **周初 20–30 分钟** | 四人组会：确认本周可交付功能、逐项分配 Issue、风险依赖 | `meetings/Wxx.md`，记录议题/结论/负责人/期限 | 对应协作与任务记录 |
| **每次编码前** | 选择一张 Issue，明确输入、输出、接口、验收场景；只学习本任务所需的工具 | Issue 描述和验收条件 | 避免无目标学框架 |
| **开发中** | 各组独立分支提交；接口变更更新 OpenAPI，前端优先用 Mock 保持并行 | 提交、PR、接口变更记录 | 可追溯与可联调 |
| **每个模块完成时** | 本人先跑正常、边界、异常测试；另一个人 Review/复测；合并后跑基础回归 | 测试用例、结果、Bug Issue、修复提交 | 保证质量而非期末补测 |
| **周中 15–30 分钟** | 前后端联调并确认是否有阻塞；必要时演示真实数据链路 | 联调简记/阻塞清单 | 防止最后才集成 |

**Bug 闭环定义**：复现步骤 → 预期/实际结果 → 日志/截图 → 修复 PR → 回归结果。  
**功能完成定义（DoD）**：代码已合并、接口文档已更新、正常和关键异常用例通过、可在目标环境运行、留下必要证据。  
**学会的最低标准**：能够自己解释本模块数据流、独立修改一个需求并排查常见错误；AI 生成内容必须人工验证后才采纳。

## 4. 工期风险与变更规则

1. **硬门槛优先**：M1 网络链路、M2 CRUD、M3 借还事务、M4 基础完整性不通过，不继续扩展创新。
2. **实际资源不足时削减顺序**：先不做分类推荐 → 不做 Android → 缩减超期提醒范围 → 暂缓批量导入导出；保留已完成且可靠的联网与统计，并把资源投入核心质量。**已明确的课程基础功能、测试和文档不能删**。
3. **范围冻结**：W11 冻结基础需求；W13 冻结桌面新增功能；W14 优先终验，Android 通过门槛才做；W15 不新增功能。
4. **基础质量优先于新功能**：遇到复杂并发或数据库故障，先确保正确性、恢复能力和测试记录，不追求吞吐量数字。
5. **变更要留痕**：每次功能增减在 Issue/`docs/decisions.md` 记录日期、原因、对评分覆盖的影响及新验收标准。
