## 1.2 接口与集成协作

每项任务写明负责人、评审人、依赖接口、预期交付和验收证据。dhw与lkx维护公共接口约定，zyj更新自己负责的字段、分页与查询条件，hyq核对页面所需字段。接口变更先记录OpenAPI，再通知调用方，更新Mock和用例；Mock仅用于并行开发，周验收必须使用真实公网链路。

前端代码由同组另一人评审，后端同理；跨端联调由界面负责人和API负责人共同执行。发现错误时记录请求、响应、时间、版本和脱敏日志，按UI、请求、Controller、Service、Repository、数据库顺序定位。公共模块阻塞由dhw或lkx牵头解决，页面和CRUD成员继续做不依赖该阻塞的工作。

## 二、系统功能要求

系统按读者与管理员两类角色组织功能。下表列出业务范围，其中续借、预约等扩展功能不属于本轮必做范围，具体执行第四章的周任务。

| **功能模块** | **主要功能** |
| --- | --- |
| 读者端 | 登录、图书查询、借书、还书、续借、图书预约、个人资料及借阅记录查询 |
| 管理端 | 图书信息增删改查、图书分类管理、读者信息管理、借还书记录管理、用户及权限管理、逾期借阅管理 |

功能之外，还需要考虑数据库的数据一致性、权限控制、系统可靠性和操作便捷性。

## 三、项目开发报告要求

报告必须包含以下六部分：

1. 项目概述：项目基本内容、组长与成员、成绩分配方案、任务分解和人员分工。

2. 业务需求分析和基本模块功能：业务场景、用户需求、模块功能。

3. 系统设计与实现：技术平台及架构、功能详细设计、数据库字典、必要时的 UML 类层次图、一个代表性功能的编码实现。

4. 系统测试：测试方案、测试用例及测试结果。

5. 项目展望：不足与后续改进方向。

6. 附录：至少两次小组会议纪要。

## 四、评分与交付规则

项目按七项维度评分，共100分，具体检查项见第五章。普通成员原则上获得相同项目分数，组长为项目分加2分。正常履行分工职责的成员，不因任务类型、工作量或技术难度存在合理差异而区分分数。个别成员基本未参与、未履行任务或几乎无实际贡献时，组长可提交书面说明与证据，由教师或助教审核；经核实原则上每降低一个等级扣2分，严重情况另行处理。组长由小组确认。

具体提交日期和方式按教师后续通知执行。项目组需提交可运行程序、源代码、数据库脚本或配置说明、完整开发报告及至少两次正式组会纪要，并完成演示和答辩。

## 0. 项目范围与排期总则

### 0.1 边界与优先级

**（1） 必须首先完成**：基于 Qt + MySQL 的图书管理系统；借书人端与管理员端；图书、读者、借还和借阅记录；业务异常处理；良好的代码结构、数据库一致性、UI、测试、协作过程和文档。

### 本周四人任务与学习安排

### dhw

**开发任务：** 建立Qt/CMake工程、QML首页与列表、公共异步网络封装；接入公网HTTPS图书接口。

**学习内容：** Qt对象与信号槽、QML属性绑定和ListView、Qt Network与JSON、TLS错误识别。

**练习与学习成果：** 独立写一次按钮请求，将真实JSON显示为列表；故意配置错误地址再恢复；将成果用于本人模块，提交可运行代码或练习记录。

**本周交付物：** Windows最小客户端、网络模块初稿、架构图客户端部分。

**联调与测试：** 和lkx验证Nginx到Drogon，和zyj核对真实图书字段；测加载、失败和数据库重启后查询。

**个人验收：** 全新Windows客户端查询云端MySQL数据；解释请求至页面更新过程，不绕过证书验证。同组另一人复核代码，接口搭档复核端到端结果，保存提交与测试证据。

### hyq

**开发任务：** 搭建管理员页面骨架和通用表单，调用dhw网络模块展示真实图书列表。

**学习内容：** QML布局、控件、属性绑定、ListView委托、JSON字段含义。

**练习与学习成果：** 做含列表和输入框的页面，显示公网接口真实记录，切换加载空数据状态；将成果用于本人模块，提交可运行代码或练习记录。

**本周交付物：** 管理员布局初稿、列表界面、UI规范初稿。

**联调与测试：** 与dhw对接调用方式，和zyj核对列表字段，参与M1演示。

**个人验收：** 能独立改字段显示；M1页面数据来自云端，不能仅用静态Mock。同组另一人复核代码，接口搭档复核端到端结果，保存提交与测试证据。

### lkx

## 0. 使用规则与开发边界

**标注说明**

• **【课程要求】**：评分方案 明确提出的项目、交付或考查要求。

• **【评分示例】**：用于对应评分维度的业务与创新示例。组员按项目已确定的范围执行；创新不追求数量，优先完成有实际价值且能稳定运行的功能。

• **【验收细化】**：把教师的定性要求转换为可操作的验证方法，不是教师额外规定的新功能。

• **【自选进阶】**：可选的创新方向，依实际进度选择；**手机端最后做**。

**范围原则**：仅围绕 图书管理的功能展开，不新增座位预约、智能扫码等 评分方案 未提及的业务功能。联网采用既定的 C++ + Qt 客户端 / Drogon 后端 / MySQL 云端架构，**从最早的系统骨架就接入**，但独立网络服务在课程上属于进阶内容而非必需项。技术复杂度不直接等于高分。

## 工期风险与变更规则

1. **硬门槛优先**：M1 网络链路、M2 CRUD、M3 借还事务、M4 基础完整性不通过，不继续扩展创新。

2. **实际资源不足时削减顺序**：先不做分类推荐 → 不做 Android → 缩减超期提醒范围 → 暂缓批量导入导出；保留已完成且可靠的联网与统计，并把资源投入核心质量。**已明确的课程基础功能、测试和文档不能删**。

3. **范围冻结**：W11 冻结基础需求；W13 冻结桌面新增功能；W14 优先终验，Android 通过门槛才做；W15 不新增功能。

4. **基础质量优先于新功能**：遇到复杂并发或数据库故障，先确保正确性、恢复能力和测试记录，不追求吞吐量数字。

5. **变更要留痕**：每次功能增减在 Issue/docs/decisions.md 记录日期、原因、对评分覆盖的影响及新验收标准。

# 第七章 测试记录与交付模板

## 7.1 每周测试安排

第8周冒烟及持久化，第9周CRUD和权限，第10周借还专项与并发一致性，第11周P0首轮整体验收，第12周回归、统计和多终端，第13周创新与小规模并发，第14周全量终验、备份恢复和模拟答辩，第15周干净环境复现及最终回归。每次测试保存可复现步骤和实际结果；并发验证以业务正确性为目标，不设无依据的吞吐量指标。

## 7.2 核心场景责任与核查方法

| **场景** | **执行搭档** | **数据与结果核查** | **计划阶段** |
| --- | --- | --- | --- |
| 公网图书查询 | dhw、lkx | zyj核对SQL，hyq核对显示；记录HTTPS地址和各层日志，数据库重启后复查 | W8 M1 |
| 登录及权限 | dhw、lkx | hyq用读者身份尝试管理操作，zyj复核API拒绝结果；不仅测按钮可见性 | W9 M2 |
| 图书读者CRUD | hyq、zyj | dhw从读者端重查；引用删除规则按设计验证；非法和重复字段有反馈 | W9 M2 |
| 借查还及重复操作 | dhw、hyq、lkx | zyj核对副本、记录、库存口径；重复借还不产生额外业务结果 | W10 M3 |
| 争抢同一副本 | lkx、zyj | 两会话同时请求，仅一次成功；核对活跃记录与状态，不只看HTTP成功数 | W10 M3及后续回归 |
| 事务失败回滚 | lkx、zyj | 在受控测试环境触发事务内失败，前后状态一致，无部分更新；记录触发方法 | W10 M3 |

| 干净环境与正式提交 | 四人 | 程序源码脚本文档对应同一版本，实际提交渠道按教师通知 | W15 M8 |

## 7.6 最终报告与提交包组织

提交开发报告时，按以下六部分组织：项目概述与分工、需求与模块、系统设计与实现、系统测试、项目展望、附录组会纪要。实现章节应补入最终数据字典、必要UML及真实代表性代码，测试章节填实际结果，展望写真实不足，不把计划目标写成既成成果。
